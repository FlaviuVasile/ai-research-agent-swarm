# Agentic RAG gap analysis

## Runtime classification

Conventional RAG conditions generation on evidence fetched from a retrievable source. The FAST Orchestrator meets that definition through FTS5/BM25 and selected PDF passages. The persistent corpus independently supports BM25, local Ollama semantic retrieval, and hybrid reciprocal rank fusion. FULL and standalone FAST summary/questions use chunking or spread excerpts, not ranked corpus search. The literature stage uses model-generated questions to query OpenAlex, then rates titles; it is external metadata discovery, not full-text retrieval for the manuscript agents. [Orchestrator](../orchestrator.py), [selector](../research_swarm/summary_work.py), [retrieval](../research_swarm/corpus/retrieval.py), [service](../research_swarm/service.py), [literature agent](../agents/literature_agent.py)

The corpus QA feature adds two materially different behaviors. Its default `spans` strategy decomposes the question with deterministic rules, retrieves once per part, and asks the model to select exact source spans. Its `legacy` strategy can use an evidence gap or failed draft to drive one more retrieval/draft attempt, and validates quotes, numeric tokens and model-assessed support. This is a bounded **Agentic RAG prototype by runtime behavior**, not just by name. However, the current Streamlit and MCP callers omit `strategy`, so their user-facing `ask_scientific_question` path remains one-pass `spans`. The fixed four-agent Orchestrator never invokes this adaptive QA loop. Therefore: **RAG is already implemented; Agentic RAG is present only as an internal opt-in path and is not the default end-to-end system.** [QA](../research_swarm/corpus/qa.py), [corpus UI](../research_swarm/corpus/ui.py), [MCP server](../research_swarm/mcp_server.py), [Orchestrator](../orchestrator.py)

| Gap | Consequence | Proposed acceptance evidence |
| --- | --- | --- |
| Fixed FAST query emphasizes generic domain/section terms | Relevant methods, numerical results and limitations may miss the candidate pool. Its effect has not been measured. | Compare the shipped selector against task/field-aware BM25, semantic and hybrid using judged evidence and matched context budgets. |
| Main analysis does not use all available retrieval modes | Semantic and hybrid exist in corpus search, but only BM25 is used by FAST analysis; FULL is map/synthesis. | Test retrieval strategies independently and integrate a winner only if recall/quality gains justify the indexing and latency cost. |
| Retrieval scores/selection policies are not a measured relevance guarantee | Hybrid RRF and the fixed FAST heuristic are implemented, but no gold-set precision/recall is reported. | Use frozen query-to-span labels, score candidates and packed context at k, and report paired differences. |
| Main summary/question claims are not bound to citations | QA exact-span citations do not flow into the main Summary/Questions outputs; prompt instructions and source exposure are not validation. | Require all material claims to cite resolved spans and measure resolution and support separately. |
| Evidence sufficiency/feedback is not enabled on normal UI/MCP QA | `legacy` can request a follow-up, but public callers use one-pass `spans`; the main Orchestrator has no feedback edge. | Expose an explicit opt-in only after comparing no-loop, checks-only, same-context revision and retrieval-plus-revision. Include sufficient, recoverable and unanswerable traces. |
| QA validation is heuristic/model-based, not an independent oracle | Exact quote and numeric checks establish provenance/consistency, while semantic support is judged by the same model family and can miss nonnumeric overclaims. | Test claim-level false acceptance/rejection against blinded human judgments and retain raw traces. |
| FAST, FULL, standalone MCP and corpus Q&A have different evidence semantics | A mode name alone does not ensure the same retrieval or coverage across entry points. | Document each contract; add integration tests for mode, scope, retriever, evidence manifest and saved output. |
| Limited outcome evaluation | The three-abstract prompt pilot cannot establish retrieval or agentic-loop improvement on full papers. | Paired held-out full-paper evaluation with reviewer agreement, failure counts and latency/cost ablations. |

## Should agents retrieve independently?

There is already one bounded adaptive retrieval prototype in `CorpusQA(strategy="legacy")`; do not duplicate it. First establish how it behaves on frozen, labelled multi-page questions and compare it with the current default `spans` strategy. If it helps, expose it as an explicit, versioned UI/MCP option and keep the shared service/controller responsible for document scope, limits, deduplication and trace persistence.

For the main agents, do not give every agent an unrestricted independent retriever. Prefer a typed request such as `{field_or_claim, reason, query}` from Summary or Questions to a controller-owned search. A follow-up should only happen for an explicit missing field/unsupported claim, under the same authorized document scope and a shared small budget. Keep OpenAlex discovery separate from manuscript verification; title metadata cannot resolve manuscript findings. Stop on sufficient evidence, no new hits, repeated queries, timeout, or exhausted attempts, and preserve an unresolved outcome. See the [target design](TARGET_ARCHITECTURE.md) and [experiment](RAG_EVALUATION_PLAN.md).

The corpus already uses local SQLite FTS5, persisted model-identified Ollama vectors, a bounded exact cosine scan and RRF; a second vector database is not justified by the current scale or evidence. The immediate gap is measured ranking and integration, not missing vector infrastructure.
